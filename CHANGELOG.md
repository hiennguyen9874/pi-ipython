# Changelog

## [Unreleased]

### Added

- A default prelude of stdlib imports (`json`, `os`, `re`, `sys`, `time`, `math`, `shutil`, `itertools`, `functools`, `collections`, `textwrap`, `Path`, `datetime`, `timedelta`, `Counter`, `defaultdict`) runs in every Kernel, including after a Kernel replacement, so Cells can use them without importing. The system prompt lists the prelude, and the Python-state notice leaves its names out like other bootstrap names. (#44)
- `prelude` config: `prelude.defaults: false` drops the default imports, and `prelude.imports` adds import statements (global and project entries concatenate). Entries that are not a single absolute import statement are reported and skipped; an import that fails in the Kernel is reported as a warning and the rest still run. (#45)
- The prompt's prelude line names the stdlib defaults instead of repeating their import statements and says they exist only in the REPL, so files and scripts the model writes keep their own imports. Configured imports get their own sub-line, marked as installed for the project, so the model uses them instead of probing or installing alternatives. (#46)
- `prelude.prompt: false` leaves the prelude out of the system prompt while the Kernel still runs it. (#47)
- `backgroundNotices: true` (TUI and RPC only) sends the model a Background-command notice, `[bash-done pid:N exit:M]` with the command, when a `bash()` handle that outlived its Cell finishes. Notices wait until pi is idle and then start a turn. They are batched until no other Background command runs, or for at most 2 minutes. A read of the handle before delivery withdraws its notice. After 5 wake-up turns in a row, or a user abort of one, notices wait for the user's next message. Queued notices are dropped on shutdown and Kernel replacement. With the switch on, the system prompt tells the model to end its turn instead of sleeping on long commands. (#26)
- A running Cell streams its output live to the TUI: stdout, stderr and Background output appear as they arrive, collapsed to their tail, with a `Running… 12.3s` line. Partial updates are throttled to one every 100 ms like pi's bash tool, cut to the output limits, write no Spill file, and stop when the Cell's result is returned. The model never sees them, and the final result is unchanged. RPC clients get the tail as text, with a `[Output truncated (… so far): …]` notice when cut. (#23)

### Fixed

- Live Cell output review fixes: `Running…` starts when the Cell is sent to the Kernel, not during startup or a busy-Kernel prompt. Expanding the live row shows each bounded stream tail and the Background output label. The RPC tail respects the byte limit even when that label only fits in the truncation notice. Final results and Spill files are unchanged. (#23)

- Cell output no longer grows pi's memory or session file without bound. Each stream (stdout, stderr, Background output) keeps a bounded tail and begins spooling as soon as either configured output limit is crossed. The Spill file preserves the original text, including Unicode across frames, and `details` stores only the tails. Intermediate spools are removed after assembly or on Kernel loss. A failed spool write keeps the Cell running and reports why full output could not be saved. One resize worker keeps the last eight images in arrival order, including Background displays; drop notices remain visible outside the truncated text. (#19)
- A Background command (a `bash()` handle that outlives its Cell) that finishes no longer adds a misleading `Background bash completion follow-up … was not accepted` warning to the next Cell's background output. The host now acknowledges the runtime's `bash.completed` and `bash.consumed` requests whether or not a Cell is running, without notifying the model; other host requests from finished Cells are still rejected. Real-session regressions cover completion between Cells and during another Cell. (#49)

- State-loss notice review fixes: collapsed Cell-loss diagnostics now show a bounded stderr preview while keeping the exit cause visible and preserving the full expanded/model result. `/tree` Keep and dismissed choices now send hidden branch notices, matching the other lifecycle notices. Real-session regressions cover large-stderr crashes and hidden Keep/dismiss notices. (#42)

- State-loss notices no longer imply a Kernel existed or that external effects were undone. Lifecycle notices are hidden from the UI but still reach the model; `/tree` restart gives a short confirmation, and Cell loss results are concise and expandable. Branch summaries and compaction entries trigger conservative warnings on session start; a clean `/new` remains quiet. (#42)

- A clean `/new` session no longer sends a State-loss notice when its branch has no earlier Cells or summaries. Sessions with earlier Cells or summaries and explicit resume/fork sessions still receive a hidden notice. (#41, #42)

- Pi tool bridge review fixes: successful structured `null` results remain Python `None` instead of falling back to text, and failed calls attach only dicts to `pi.ToolError.result` (other JSON values become `None`). A real-session regression covers null, boolean, number, string, array, and object results. (#37)
- Prompt discovery tests now execute a Cell through the real Kernel before accepting the describe-before-use guidance. The v3 PRD also cross-references the existing MCP resource behavior. (#36, #38, #40)

- Pi tool search ranks a full tool-name match above namespace-suffix matches, even when a namespaced tool has a higher BM25 score. Searching `echo` with `limit=1` now returns `echo` rather than `mcp__docs__echo`; a real-session regression covers this collision. (#35)

- Richer tool discovery's no-callable-tools prompt regression test now checks exact equality against the pre-#33 baseline, substituting only the date and temporary working directory. (#33)

- The system prompt includes the `pi` discovery and call instructions only when a Pi tool is callable. The condition uses the bridge's filtered tool set and is refreshed before every model request, including after late MCP registration or tools becoming hidden. The `pi` module and Cell-level MCP readiness remain unchanged; pending servers with no registered callable tools do not add prompt instructions.

- MCP tools registered by `builtin:mcp` are discoverable and callable from Cells instead of being excluded with pi's built-in file/shell tools. Cells declare that they reach Pi tools so MCP connections finish registration before Python discovery runs. Hidden tools stay unavailable and Bridged calls keep pi's permission hooks.

- Pi tools registered during a Cell are activated before discovery or Bridged calls, including initially inactive `direct` tools. They can be called immediately while their declarations stay hidden from the model. (#31)

- Bridged calls reject background tasks whose originating Cell has finished, and calls without a Cell context, with `pi.ToolError` before dispatch. They cannot borrow a later Cell's tool context or signal; concurrent calls from a live Cell remain supported. (#30)

- Python-state notices are capped at 50 eligible names and 2,000 UTF-16 code units, report omissions and filtering, escape unusual names, and distinguish a failed listing from an empty one. Listing avoids invoking user-defined string-subclass methods; the Kernel still sends the full `list_names` response to the host. Runtime rebuilds refresh uv's cached local wheel so changed sources are installed. (#21)

- Cell rendering clips expansion hints on narrow terminals, applies configured output limits before colouring, keeps large exception messages compact, and preserves warnings when saving full output fails. (#12)

- Compaction namespace listings preserve buffered background text and images for the next Cell. Python-state notices reach the immediate continuation or overflow retry without extra model turns or duplicate notices. Real-session tests cover mid-run threshold/overflow delivery and failed, timed-out, and busy-Kernel listings. (#10)

- Killing a busy Kernel reports the loss of Python state even if replacement startup or execution fails. Interrupt tests use a deterministic interrupt-ignoring Cell and distinguish POSIX synchronous interrupts from cross-platform async interrupts. (#9)

- Branch switches in RPC mode keep the Kernel and notify the model without requesting a selection, even with a dialog-capable RPC UI. (#8)

- Lifecycle cleanup preserves live hosts with unknown identities, never kills historical process groups without ownership proof, and retains journals after unresolved cleanup. Windows Kernels contain ordinary subprocesses in a kill-on-close job. Explicit resume/fork sessions receive a State-loss notice even without earlier Cells; a clean `/new` does not. (#41, #42) After a POSIX host crash, groups whose leaders have already died are deliberately skipped because their ownership cannot be established safely. (#7)

- Cell output spills are owner-only and preserve the Cell result if saving fails. Background text is preserved in full (including literal truncation markers), keeps its attribution after tail truncation, and background image displays are delivered with the next result. (#5)

- Config reports inherited property names as unknown keys instead of failing to load, and rejects Python versions below the runtime's minimum (3.11) so defaults apply.

- Kernel pipe errors fail the Cell instead of crashing pi; a later Cell can start a fresh Kernel.
- Bootstrap locks are published with their owner atomically, reclaim stale locks with identity checks, and recover abandoned ownerless directory locks.

### Added

- The system prompt's `pi` section tells the model to call `await pi.describe(name)` before first using a tool, to read its schema, guidelines, and returns. The listing format and its 3000-token budget are unchanged; without callable Pi tools the prompt is unchanged. (#40)
- `pi.search(query, limit=8, namespace=None)`: with `namespace` (a name or alias, matched as `pi.describe_namespace`), only that namespace's callable tools are ranked with BM25, then `limit` applies. A namespace with no callable tools raises `pi.ToolError`; a non-str or empty `namespace` raises `TypeError`. Without `namespace`, results are unchanged. The prompt's `pi.search` line shows the parameter; without callable Pi tools the prompt is unchanged. (#39)
- MCP resources from Cells, with no API change: pi's `list_mcp_resources`, `list_mcp_resource_templates`, and `read_mcp_resource` (from `builtin:mcp`) are callable with `pi.tool` and return their JSON payloads as dicts. They take the widest exposure of the non-`hidden` servers with resources, so by default they are not listed but `pi.tools()` and `pi.search` find them, and they never reach `hidden` servers. A real-session test with a local stdio MCP server covers listing and reading by URI, a `hidden` server, and their absence when only a `hidden` server has resources; the README documents it. (#38)
- `pi.ToolError.result`: a failed Bridged call to a tool that declares `outputSchema` carries its error result's `structuredContent` (a dict), for example an MCP tool's whole `CallToolResult` with `isError`. It is `None` for tools without an output schema, hook-blocked calls, invalid arguments, unknown tools, and calls after the Cell finished. The message stays the tool's error text. (#37)
- Pi tool search: `await pi.search(query, limit=8)` ranks every callable Pi tool, listed or not, with BM25 over the name, description, parameter schema, and namespace (ported from pi's tool search, which its package root does not export) and returns entries shaped like `pi.tools()`, best match first. A query that is exactly a tool's name ranks it first. An empty or non-str query raises `TypeError`; a non-positive `limit` raises `ValueError`. The system prompt mentions it only inside the `pi` section, so without callable Pi tools the prompt is unchanged. New config key `piTools.search` (default `true`); `false` makes calls raise `pi.ToolError` and leaves it out of the prompt. (#35)
- Listed Pi tools: the `ipython` description (set in `prepareLoadout`) lists callable Pi tools with `direct` or `codemode` exposure, by name and first description line, grouped by namespace (namespace-less tools first, then namespaces by name with their description). Entries share a fixed budget of 3000 estimated tokens round-robin across namespaces, as codemode's catalog does; a namespace that does not fit is marked `(some tools not listed)` or `(tools not listed)`. `deferred` tools, including MCP tools with the default exposure, are never listed, so connecting MCP servers leave the description unchanged. With no listed tool, or with the new config key `piTools.list: false` (default `true`), the description is exactly as before. (#34)
- Richer Pi tool discovery: `await pi.describe(name)` also returns the tool's prompt `guidelines` (a list of str), which never reach the model otherwise, and `returns` (its output schema, or `"str"`). `await pi.describe_namespace(name)` returns a callable tool's namespace as `{name, description, instructions}`, for example an MCP server's instructions, and raises `pi.ToolError` for unknown names. The system prompt's `pi` section mentions it. (#33)
- Bridged call lifetime is covered by tests through a real session: aborting a Cell aborts its in-flight Pi tool, which sees its signal, and Python state is kept. A background `pi.tool` call made after its Cell returned raises `pi.ToolError` without running the tool. Concurrent calls in one Cell each get their own result, and `confirmEachCell` asks once per Cell, never per Bridged call. The README safety section explains that Bridged calls go through pi's hooks and permission checks while direct Python stays unsandboxed. (#32)
- Pi tool discovery: `await pi.tools()` lists the callable Pi tools live (`name`, first description line, `namespace`), and `await pi.describe(name)` returns a tool's full description and parameter JSON schema, raising `pi.ToolError` for names outside the callable set. The system prompt explains `pi` and how to discover tools without listing any. (#31)
- Bridged calls: a Cell can run `await pi.tool(name, args)` to call a Pi tool through pi's `ctx.executeTool`, so argument validation, `tool_call`/`tool_result` hooks, and permission checks apply. Callable: every registered tool except `ipython`, `hidden` and `model-only` tools, tools that reach other tools (`codemode`, `tool_search`), and pi's built-ins; bridged `direct` tools are activated with hidden declarations, so the model still sees only `ipython`. Tools with an `outputSchema` return their `structuredContent` (a dict), others their text (images become `[N image(s) omitted]`); every failure raises `pi.ToolError` (a `RuntimeError`). `pi` is a repo-owned module (`src/bridge/pi.py`) bound in every new Kernel and left out of the Python-state notice. (#30)
- TUI renderer for Cells: the call shows the Cell's code highlighted as Python (first 10 lines until expanded). The result shows the last 5 lines of output until expanded, then the exception name (bold) and message in the error colour; the traceback appears only when expanded. Stderr is shown in the warning colour, background output is dimmed, a Kernel restart, an aborted Cell, and a truncated-output path get a warning line, and images the terminal does not draw get a placeholder. Cells that never ran (refused, busy Kernel) show the reason as an error. (#12)
- `confirmEachCell`: when on, the user sees each Cell's code and approves it before it runs. A rejected Cell does not run (no Kernel is started for it) and the model gets a "Cell rejected by user" error result. Without a UI, every Cell is refused with an error saying confirmation is on but there is no UI. Off by default. `README.md` documents installing and enabling the package, the config keys, and the safety model: the Kernel runs with the user's permissions, is not a sandbox, bypasses pi's tool-call guards, and should run in a container for untrusted work. (#11)
- Python-state notice: after every compaction (manual, threshold, or overflow) while a Kernel is running, the model gets a hidden `[python-state]` message (custom type `ipython_state`) listing the live user-defined names from the Kernel (`list_names`), following Unharnessed's wording. No notice is sent when no Kernel is running. If listing fails, times out after 5s, or the Kernel is still busy with an interrupted Cell, the notice is sent without the names. When idle, the notice is appended right after the compaction, so back-to-back `/compact` runs each add a fresh one. During a run, it is included in the next model request and persisted at the end of the current turn. (#10)
- Interrupt and busy Kernel: aborting a Cell (Esc) interrupts it with `KeyboardInterrupt` and keeps Python state. If the Cell ignores the interrupt, its tool call returns after 1s anyway. The next Cell keeps re-sending interrupts for up to 5s. If the Kernel is still busy after that, the TUI asks whether to wait (keeping state) or kill the Kernel. After a kill, the pending Cell does not run; its error carries the State-loss notice, and the model can resubmit after accounting for lost state (ADR 0003). Without a TUI, or when the choice is dismissed, the model gets a "Kernel busy" error. (#9)
- Branch switch: after a `/tree` navigation with a running Kernel, the user picks "Keep Kernel" or "Restart Kernel". Restart kills the Kernel (the next Cell starts a fresh one) and the model gets the state-lost notice; Keep (also the default when the choice is dismissed or there is no UI) leaves Python state intact and the model is told it may not match the branch. (#8)
- Session lifecycle: `session_start` warms the uv venv in the background (the Kernel still starts on the first Cell). Every `session_shutdown` kills the Kernel and its process group, including subprocesses started by Cells. Kernels are journaled per pi host under `<agentDir>/pi-ipython/journal/`, and Kernels (plus their `bash()` children) left by a crashed host are reaped the next time the extension starts. When a session starts with earlier `ipython` Cells on its branch (resume, fork, reload, `--continue`), the model gets a notice that Python state is gone with its next turn. (#7)
- Forced system prompt: pi's prompt is replaced by an Unharnessed-style REPL prompt (one `ipython` tool, `bash()` handles, no `%magic`/`!cmd`), followed by pi's context files, the skills list with `SKILL.md` paths to read from Python, the current date, and the cwd. (#6)
- Cell output shaping: the result text is truncated to its tail at `output.maxLines` / `output.maxBytes` (pi's 2000 lines / 50KB by default), with the full text spilled to a temp file whose path is in the result. `display` payloads with image MIME types (png, jpeg, gif, webp) become image blocks. stdout/stderr with no owning Cell (threads, subprocesses, tasks of finished Cells) is buffered and appended to the next Cell's result under `[background output]`. (#5)
- Config: `<agentDir>/pi-ipython.json` (global) merged with `.pi/pi-ipython.json` (project), project values winning per key. Keys: `confirmEachCell`, `python.source` (`uv` | `project`), `python.version`, `output.maxBytes`, `output.maxLines`. Invalid files, values, and unknown keys are reported with the file and key and skipped, so defaults apply. `python.source: "project"` runs the Kernel with `<cwd>/.venv`'s Python and the vendored runtime on `PYTHONPATH`. (#4)
- `ipython` tool, the only active tool while the extension is loaded. Each call runs one Cell in a persistent Kernel (`python -m rlm.repl`, REPL protocol v3) started lazily in the session cwd; the result carries stdout, labelled stderr, the trailing expression's repr, errors with tracebacks, and the duration. (#3)
- Kernel bootstrap: a uv-managed venv (Python 3.13) built from the vendored runtime's lockfile on first use, rebuilt when the runtime changes, guarded by a directory lock. Location: `<agentDir>/pi-ipython/kernel-venv-<version>`, overridable with `PI_IPYTHON_VENV_DIR`. (#3)
- Kernel client ported from Unharnessed's pre-Rust host: spawn, `ready` handshake, JSONL framing with frame validation, routing by Cell id, interrupt on abort, shutdown. (#3)
- Pi package skeleton: `package.json` manifest with an empty extension entry (`src/index.ts`). (#2)
- Vendored Kernel runtime (`rlm`) from Unharnessed `fe2cf281` under `runtime/`, with its pytest suite run under uv (Python 3.13). (#2)
- Integration test harness (`test/harness.ts`): a real pi SDK session with pi-ipython loaded through extension factories and a faux model. (#2)
- `npm test` runs vitest and the runtime's pytest suite together. (#2)
